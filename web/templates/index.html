      Methodology

      How Glitch Hunter works

      Each objective builds on the one before it. Objective 1 gives the project an AI that can play; Objective 2 turns it into a tester; Objective 3 turns what it finds into evidence and reports.

      1Objective 1
      An AI that can play

      Game environment

      Super Mario Bros Level 1-1 (a Python copy of the game), wrapped as a standard AI environment. Two copies: clean and bugged.

      Autonomous agent

      A PPO brain learns from the screen alone which buttons move Mario forward and finish the level.

      3Objective 3
      Automatic bug reports

      Bug detection

      The rules checked on every frame: never inside a solid, never stopped by something invisible, never hurt without contact, never an impossible jump or speed.

      Evidence capture

      The exact frame, the movement history and every button press are saved; testing pauses.

      Replay check

      A separate process replays the run from its start to prove the bug happens again.

      Bug reporting

      A GIF, a Markdown and a PDF report and a downloadable evidence bundle are written. The report also points to where to fix the bug in the game's code.

      Final QA result

      Bugged game: every bug in the Bug Tracker. Clean game: a "No Bugs Found" run report.

      Why there are two games

      Clean game

      The original level, never modified; its files are locked by a fingerprint. Every brain was trained and measured on it. Any report here would be a false alarm, so it is how the project proves the detectors stay quiet.

      Bugged game

      An exact copy with known deliberately planted benchmark bugs, each declared in a list and marked in the code. The detectors are general rules and do not know where any bug is; this is how the project proves they find real bugs.
